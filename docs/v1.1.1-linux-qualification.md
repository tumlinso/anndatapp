# AnnData++ 1.1.1 Linux qualification

AnnData++ 1.1.1 adds [dense binary16 storage](fp16.md) to the standalone
C++20 library and its eager and backed H5AD and Zarr paths. Dense AnnData
payloads retain binary16 in MuData and TreeData. Dense H5AD collections
can transfer into caller buffers and materialize FP16, and SpatialData image
rasters can use FP16. Existing sparse encodings and dtypes are preserved.

## Native and installed-package checks

Linux x86-64 native qualification passed 284 executions across nine
configurations. The installed package passed clean `1.1.1 EXACT` CMake
consumers covering FP16 in the dependency-free core and both full-library
import facades.

| Configuration | Passed |
| --- | ---: |
| Debug, Release, shared Debug, shared Release | 39 each |
| ASan/UBSan | 39 |
| Focused TSan | 4 |
| Core-only | 22 |
| HDF5-only | 33 |
| Zarr-only | 30 |

The ASan/UBSan run used the maintained settings with leak detection disabled.
TSan covered streaming and prepared transfer paths. Dense FP16 native tests
check signed strides, exact stored bits, and format-family selections.

The full interoperability configuration passed 55/55 checks, and the
separate shared Parquet installation passed 3/3. Python AnnData independently
wrote and reopened dense FP16 H5AD and Zarr v2/v3. The tests cover `X`,
layers, `obsm`, `.raw.X`, both byte orders, selected transfers, missing
chunks, and rejection of FP16 CSR and CSC through native I/O. Supplemental
checks covered Scanpy records, HDF5 links, and legacy MuData reopen.
The [Linux machine receipt](../tests/results/v1.1.1-linux.json) records the
exact configured matrix and source manifest.

## Regression comparisons against 1.1.0

The same native driver and fixtures validated all 38 operations against
v1.1.0 and the v1.1.1 production source. The [regression receipt](../benchmarks/results/v1.1.1-regression.json)
also includes the one- and four-worker streaming runs, module import timings,
and separate allocation and I/O diagnostics.

An early candidate slowed in-memory gathered selection acquisition by about
15% on two cores. The selection code and allocations matched the baseline.
Moving the new binary16 conversion implementation into a separate translation unit
restored the relevant code alignment in the test build. The final
`gather_select` run had a 1.016 paired ratio and overlapping sample ranges.

The remaining flag was an in-memory CSC opposite-axis gather copy. Eight
copies took 0.320 ms on v1.1.0 and 0.361 ms on the candidate, with a 1.139
paired ratio and equal allocation counts and bytes. Follow-up paired ratios
were 1.075 with overlapping ranges on one core and 1.051 with separated ranges
on the other. The source copy and preparation loops were unchanged. The
result remains a scoped performance limitation. None of the four streaming
comparisons met the regression threshold. The four-worker Zarr median fell
from 486.5 to 368.9 MiB/s with overlapping time ranges and identical
backend read and scratch counts.

A fresh core consumer took about 0.131 s against each installed revision.
Three consumer-only recompiles had medians of 0.172 s and 0.168 s. The
consumer still imports five BMIs. Private HDF5 and Zarr edit/restore
checks preserved 16 BMIs and three consumer objects.

## Dense FP16 performance

The [dense benchmark](../benchmarks/fp16/README.md) used equivalent 4,096 ×
1,024 FP16 and FP32 matrices on Linux x86-64 with Clang 18.1.3 and HDF5 1.10.10.
All 16 operations passed independent output checks. Five alternating samples
per arm measured the operation separately from setup on one physical core
with warm OS caches. Read fixtures had matched chunk and shard geometry.
Eager writers used the same settings and chose their normal output chunk
geometry for each dtype.

| Operation | FP16 median | FP32 median |
| --- | ---: | ---: |
| 32 dense copies into caller storage | 19.83 ms | 41.66 ms |
| Two eager reads of contiguous H5AD | 15.17 ms | 29.28 ms |
| Four prepared reads from gzip H5AD | 68.29 ms | 134.25 ms |
| Four prepared reads from sharded Zarr v3 | 45.80 ms | 76.22 ms |
| One sharded Zarr v3 prepared update | 7.64 ms | 20.13 ms |

Measured native operation medians were 1.55–2.63× faster with FP16 across the
16 cases. The observed ranges separated in 15 cases and overlapped for the
contiguous H5AD write. FP16 used half the logical dense value bytes. The benchmark reports
synthetic input generation separately, including scalar conversion to FP16.
Compression, file geometry, and the reader's backend affect time and encoded
size. Uninstrumented timing and allocation/I/O diagnostics are recorded
separately in the [machine receipt](../benchmarks/results/fp16-1.1.1.json).

Pinned Python controls read the same FP16 fixtures. Native FP16 was faster in
10 of 11 default-stack comparisons. The exception was the prepared gzip
H5AD read at 68.29 ms native versus 26.91 ms with h5py. The default stacks
used different HDF5 versions and cache budgets.

The [follow-up cache control](../benchmarks/results/fp16-hdf5-cache-1.1.1.json)
kept the h5py stack and fixture fixed. Its median moved from 27.22 ms at the
default 8 MiB chunk cache to 77.22 ms at the native 1 MiB cache setting, with
the native arm at 69.82 ms. The cache budget reversed the ordering of the
medians on this fixture. The matched h5py and native ranges overlapped.
